# บันทึกการอัปเกรดและทดสอบเว็บไซต์

วันที่ตรวจ: 21 ตุลาคม 2569 (2026-10-21), เขตเวลา Asia/Bangkok

## ขอบเขตที่ปรับ

### ฝั่ง User และฟอร์มแจ้งปัญหา

- ค้นหาเรื่อง เรียงล่าสุด/อัปเดตล่าสุด/เก่าสุด แสดง 6 เรื่องก่อนแล้วเพิ่มครั้งละ 6 เรื่อง พร้อมล้างตัวกรองและปุ่มอัปเดตสถานะ
- รายละเอียดแสดงเวลาที่อัปเดต ปุ่มอัปเดตสถานะ และข้อความยืนยันพร้อมหมายเลขเรื่องหลังส่งสำเร็จ
- ฟอร์มแบ่งกลุ่มข้อมูลและรูปภาพ แสดงจำนวนตัวอักษร ข้อผิดพลาดรายช่อง และสรุปข้อผิดพลาดที่กดไปยังช่องได้ ตรวจอาคาร/หมวดหมู่จากรายการที่เปิดใช้งาน และย้ายโฟกัสไปช่องแรกที่ต้องแก้
- เตือนเมื่อรีเฟรช/ปิดแท็บหรือกดลิงก์ออกจากหน้าขณะมีข้อมูลค้างไว้ ข้อความและรูปที่ยังไม่ส่งเก็บในหน้านั้น ไม่มีการบันทึกร่างลง localStorage หรือฐานข้อมูล
- ช่องเลือกอาคาร/หมวดหมู่รองรับรายการยาว เลื่อนตามตัวเลือก ใช้คีย์บอร์ดหรือพิมพ์เพื่อค้นหาตัวเลือก และปรับตำแหน่งตามพื้นที่หน้าจอ
- รูปที่เลือกแนบเปิดขยายดูก่อนส่งได้ ปุ่มลบมีขนาดกดง่ายและจัดโฟกัสหลังลบ ส่วนรูปในรายละเอียดเปิดหน้าต่างดูภาพ ใช้ปุ่ม/ลูกศรเปลี่ยนภาพ ปิดด้วย Escape และแสดงคำแนะนำเมื่อโหลดรูปไม่ได้

### ฝั่ง Admin

- หน้ารายการเก็บคำค้น สถานะ อาคาร ประเภทปัญหา ลำดับ และหน้าใน URL เลือกเงื่อนไขแล้วกดค้นหา/ใช้ตัวกรอง มีตัวกรองที่ล้างแยกได้และปุ่มล้างทั้งหมด
- แบ่งหน้าละ 20 เรื่อง รองรับหน้าที่เกินจำนวนหลังข้อมูลเปลี่ยน เรียงล่าสุด/เก่าสุด/รอรับเรื่องก่อน ใช้การ์ดบนมือถือ และแยกข้อความกรณียังไม่มีเรื่องออกจากกรณีไม่ตรงตัวกรอง
- Dashboard เตือนเมื่อมีงานค้างนอกช่วงสรุปที่เลือก พร้อมลิงก์เปิดคิวรวม ใช้ช่องเลือกเดือนหรือกราฟได้ทุกขนาดหน้าจอ กราฟใช้ลูกศรซ้าย/ขวา Home/End เพื่อเลื่อนเดือน แล้ว Enter/Space เพื่อเลือก
- รายงานเปิดดูรายการจากเดือน สถานะ ชื่ออาคาร และประเภทปัญหาได้ ส่งออก CSV เฉพาะข้อมูลสรุปตามช่วงที่เลือก ใช้ UTF-8 BOM สำหรับภาษาไทย ใส่เครื่องหมาย quote ให้เซลล์ และทำให้ข้อความขึ้นต้นคล้ายสูตร spreadsheet ไม่ถูกนำไปประมวลผล
- หน้ารายการและรายงานใช้ `getAdminTicketSummaries()` ไม่ดึงรูป ประวัติ หรือข้อมูลติดต่อ และไม่เรียก Storage signed URL ของหน้าที่ไม่ใช้ข้อมูลเหล่านี้ Dashboard/รายละเอียดใช้ข้อมูลเต็มตามเดิม
- การแบ่งหน้าใน UI ช่วยลดจำนวนแถวบนจอ ข้อมูลสรุปสำหรับค้นหาและนับยังโหลดครบผ่าน API แบบแบ่งหน้า ไม่ใช่การเปลี่ยนสถาปัตยกรรมเป็นการค้นหาหรือรวมสถิติที่ฐานข้อมูล

### การเข้าถึง ความเชื่อมต่อ และความปลอดภัย

- มีลิงก์ข้ามไปเนื้อหาหลัก สถานะกำลังโหลดที่โปรแกรมอ่านหน้าจออ่านได้ ปุ่มสัมผัสที่กดง่าย สถานะเปิดเมนูมือถือ และลดแอนิเมชันตามการตั้งค่าของผู้ใช้
- แจ้งเมื่อเบราว์เซอร์รายงานว่าออฟไลน์ ปุ่มอัปเดตแสดงความคืบหน้าและกันกดซ้ำขณะทำงาน ข้อความนี้ไม่ได้ยืนยันว่าบริการ Supabase พร้อมใช้งานทุกครั้ง
- เพิ่ม HTTP headers ป้องกันการฝังหน้าและ MIME sniffing จำกัด object/embed และ base URL ปิด browser APIs ที่ไม่ใช้ และลดข้อมูล referrer
- ใช้ cookie policy ร่วมกันระหว่าง client/server/proxy กำหนด Secure เมื่อเว็บไซต์ใช้ HTTPS พร้อม SameSite=Lax และตรวจรูปแบบ Supabase URL
- OAuth callback ที่แลกรหัสแล้วแต่ตรวจบัญชี/โปรไฟล์ไม่ผ่านจะพยายามล้าง session ก่อนคืนหน้าล็อกอิน และยังปฏิเสธการเข้าสำเร็จหาก Auth ขัดข้อง หน้า User/Admin/Auth คง private/no-store รวมถึงช่วง refresh cookie
- รายละเอียดและข้อจำกัดอยู่ใน [การเสริมความปลอดภัย](../03_design/security-hardening.md) การตรวจนี้เป็นการตรวจโค้ดและ regression tests ไม่ใช่ penetration test และ CSP ชุดนี้ยังไม่ใช่นโยบาย script/style แบบเต็ม

ไม่มี migration SQL หรือ dependencies ใหม่จากการอัปเกรดนี้ บทบาท Google OAuth ของมหาลัย การตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์ RLS และ RPC เดิมยังใช้งานตามเดิม ไม่ได้เปิดบริการอีเมลแจ้งเตือน Bell Toggle ยังคงเป็นการตั้งค่าทดลองในเครื่อง

| พื้นที่ตรวจ | วิธีตรวจและขอบเขต | ผล |

## สิ่งที่ทีมต้องตรวจต่อเมื่อเผยแพร่

- ตั้ง `NEXT_PUBLIC_SITE_URL` และ allowlist ของ Google/Supabase ให้ตรงกับโฮสต์ HTTPS จริง ตรวจ CDN/cache ของข้อมูลเฉพาะบุคคลตามคู่มือความปลอดภัย
- ทดสอบด้วยบัญชี User และ Admin ที่ได้รับอนุญาตจริง รวมถึงส่งเรื่อง รับเรื่อง ปิดงาน/ยกเลิก และรูป private ในสภาพแวดล้อมที่ทีมกำหนด
- ตรวจการจำกัดอัตราคำขอ การสำรอง/กู้คืน และภาระงานตามจำนวนผู้ใช้จริงก่อนเปิดวงกว้าง การตรวจชุดนี้ไม่ได้เป็น load test หรือเปลี่ยนการตั้งค่าภายในบัญชี Supabase
