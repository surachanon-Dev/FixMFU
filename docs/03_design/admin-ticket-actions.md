# รับเรื่อง อัปเดตสถานะ และปิดงาน

## ติดตั้ง

หลัง SQL 01–03 พร้อมและ Admin อ่านเรื่องจริงได้แล้ว เปิด Supabase → SQL Editor → New query คัดลอก **ทั้งไฟล์** `supabase/sql/04_admin_ticket_actions.sql` แล้ว Run หนึ่งครั้ง ไม่ต้องรันไฟล์ก่อนหน้าซ้ำ ไม่ต้องเปลี่ยนคีย์หรือปิด RLS

เมื่อขึ้น `Success. No rows returned` ให้รีเฟรชหน้า `/admin/tickets` แล้วเปิดรายละเอียดเรื่องจริง จะมีส่วน **ดำเนินการเรื่องแจ้ง** บันทึกได้เฉพาะบัญชี Google มหาลัยที่มี `profiles.role = 'admin'`

## วิธีใช้งาน

| สถานะปัจจุบัน | ปุ่ม/การดำเนินการ | ผลลัพธ์ |
| --- | --- | --- |
| รอรับเรื่อง | รับเรื่องและเริ่มดำเนินการ | เปลี่ยนเป็นกำลังดำเนินการ |
| รอรับเรื่อง / กำลังดำเนินการ | หมายเหตุ → กรอกข้อความ → บันทึกหมายเหตุ | สถานะเดิม พร้อมข้อความที่ผู้แจ้งเห็นในประวัติ |
| กำลังดำเนินการ | ปิดงาน → ระบุผลการแก้ไขหรือแนบรูป → ยืนยันปิดงานเป็นเสร็จสิ้น | เปลี่ยนเป็นเสร็จสิ้น พร้อมผลและรูป |
| รอรับเรื่อง / กำลังดำเนินการ | ยกเลิกเรื่อง → ระบุเหตุผล → ติ๊กยืนยัน → ยืนยันยกเลิกเรื่อง | เปลี่ยนเป็นยกเลิก พร้อมเหตุผล |
| เสร็จสิ้น / ยกเลิก | ดูข้อมูลและประวัติ | ไม่เปิดแก้ไขหรือย้อนสถานะ |

ข้อความยาวได้ 1,500 ตัวอักษร รูปผลการแก้ไขแนบได้ไม่เกิน 3 รูป รวม 2 MB รองรับ JPG/PNG/WebP มีพรีวิวและลบก่อนบันทึกได้ ใช้การตรวจและแปลงรูปจริงฝั่งเซิร์ฟเวอร์เช่นเดียวกับรูปแจ้งปัญหา

หลังบันทึกสำเร็จ หน้า Admin จะโหลดข้อมูลล่าสุด รายการ Dashboard และรายงานถูกล้าง cache ที่เกี่ยวข้อง ฝั่ง User เปิดรายละเอียดหรือรีเฟรชเพื่อดูสถานะ ผลการแก้ไข รูป และประวัติ ระบบยังไม่ได้ส่งแจ้งเตือนหรืออัปเดตหน้าที่เปิดค้างบนเครื่องอื่นแบบอัตโนมัติ

## การบันทึกและสิทธิ์

- Server Action ตรวจ Google session และ role ก่อนแตะฐานข้อมูล/Storage แล้ว RPC `admin_update_ticket` ตรวจบัญชีมหาลัยและ role ปัจจุบันในฐานข้อมูลซ้ำ ไม่รับ actor/role จากฟอร์ม
- ไม่มีการให้สิทธิ์ UPDATE ตาราง tickets หรือเขียน ticket_events โดยตรงแก่ client การแก้สถานะ ข้อความ รูป และประวัติทำใน transaction เดียวผ่าน RPC
- ล็อกเรื่องก่อนแก้ไข พร้อมตรวจ expected status ถ้าแอดมินอีกคนเปลี่ยนสถานะแล้ว จะปฏิเสธการใช้สถานะเก่าและโหลดข้อมูลใหม่ ไม่เขียนทับงานที่ปิดแล้ว
- เก็บ request UUID, ผู้ดำเนินการ และ payload ใน `fixmfu_private.ticket_operations` ซึ่งเปิด RLS และไม่ให้ client อ่าน/เขียน Retry ด้วย request เดิมและข้อมูลเดิมคืนผลเดิม ไม่สร้างหมายเหตุ รูป หรือประวัติซ้ำ
- ภาพผลการแก้ไขอยู่ใน Private bucket เดิม เส้นทาง `<ticket UUID>/repair/<photo UUID>.webp` อัปโหลดได้เฉพาะ Admin ขณะที่เรื่องกำลังดำเนินการ ตรวจเจ้าของและ Storage metadata จริงก่อนผูกกับเรื่อง รูป report และ repair มี UUID คนละชุดแม้ใช้ไฟล์เดียวกัน
- ปิดงานโดยใส่ metadata รูปขณะเรื่องยัง in_progress แล้วค่อยเปลี่ยนเป็น completed ภายใน transaction เดียวตามเงื่อนไข trigger เดิม รูปที่ผูกแล้วแก้ทับหรือลบผ่าน client ไม่ได้ ผู้แจ้งอ่านรูปของเรื่องตนเองได้ ผู้ใช้อื่นอ่านไม่ได้
- อัปโหลดบางส่วนไม่สำเร็จจะพยายามล้างไฟล์ใหม่ที่ยังไม่เชื่อมกับเรื่องผ่าน Storage API ถ้าผล RPC ไม่ชัดเจนจะคงไฟล์และ request ID ไว้ให้ลองซ้ำ กรณีทิ้งฟอร์ม/เครือข่ายขาดอาจเหลือไฟล์ที่ยังไม่ผูกกับเรื่อง ต้องล้างผ่าน Storage API ภายหลัง ไม่ลบ metadata Storage ด้วย SQL
- เก็บ actor UUID, role, สถานะ และเวลาจริงใน ticket_events ผู้แจ้งดูข้อความได้ ข้อความผล/เหตุผลเก็บเต็มใน tickets ส่วนข้อความประวัติที่มีคำนำหน้าถูกจำกัดตาม schema ที่ 1,500 ตัวอักษร

## ตรวจสอบ

รัน `node --test tests/auth.test.mjs tests/dashboard.test.mjs tests/report.test.mjs tests/admin-reports.test.mjs tests/admin-ticket-actions.test.mjs`, `npm run lint` และ `npm run build -- --webpack`

`supabase/tests/04_admin_ticket_actions.test.sql` ใช้เฉพาะฐานข้อมูลแยกที่จำลอง Auth/Storage สำหรับทดสอบ **ห้ามรันใน Supabase SQL Editor จริง** เพราะไฟล์ทดสอบสร้างเฉพาะ Storage metadata ไม่มีวัตถุรูปจริง Fixtures rollback ทั้งหมด ครอบคลุมรับเรื่อง หมายเหตุ ปิดงาน/ยกเลิก ข้อความยาว รูปจริงตาม metadata การ retry และสิทธิ์ User/Admin/anonymous/password/personal Gmail พร้อมตรวจว่ากฎส่งเรื่องใน SQL 03 ยังทำงานหลัง SQL 04

หลังติดตั้งต้องทดสอบจริง: รับเรื่องหนึ่งรายการ → เปิดหน้า User เห็นกำลังดำเนินการ → บันทึกหมายเหตุ → ปิดงานพร้อมผลหรือรูป → ผู้แจ้งเห็นเสร็จสิ้นและรูป → ลองอีกรายการเพื่อยกเลิกพร้อมเหตุผล → บัญชี User เรียกการดำเนินการ Admin ไม่ได้
