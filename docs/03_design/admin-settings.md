# จัดการอาคารและหมวดหมู่ในหน้า Admin

เปิด `/admin/settings` ด้วยบัญชีที่ `profiles.role` เป็น `admin` และล็อกอินผ่าน Google มหาลัย ระบบอ่านตาราง `buildings` และ `categories` จริง รวมรายการที่ปิดใช้งาน ไม่ใช้ข้อมูลตัวอย่างหรือ localStorage

## วิธีใช้

1. เพิ่มชื่อในช่อง “เพิ่มอาคารใหม่” หรือ “เพิ่มหมวดหมู่ใหม่” แล้วกดเพิ่ม ชื่อยาวได้สูงสุด 120 ตัวอักษร
2. กด “แก้ชื่อ” ที่รายการ ระบุชื่อใหม่ แล้วกด “บันทึกชื่อ” ชื่อใหม่จะปรากฏในเรื่องแจ้งเก่าที่อ้างอิงรายการนั้นด้วย
3. กด “ปิดใช้งาน” เพื่อซ่อนจากตัวเลือกในฟอร์มแจ้งเรื่องใหม่ โดยไม่ลบรายการหรือประวัติเรื่องเดิม กด “เปิดใช้งาน” เพื่อใช้ต่อได้
4. กด “อัปเดตข้อมูล” เพื่อดูการเปลี่ยนแปลงจากผู้ดูแลคนอื่น หลังเพิ่มหรือแก้รายการ ฟอร์มที่เปิดค้างในอีกแท็บต้องโหลดหน้าใหม่เพื่อรับตัวเลือกปัจจุบัน

ถ้าปิดทุกรายการของอาคารหรือหมวดหมู่ ผู้ใช้จะส่งเรื่องใหม่ไม่ได้จนกว่าจะเปิดอย่างน้อยหนึ่งรายการในแต่ละตาราง

## ฐานข้อมูลและสิทธิ์

ไม่ต้องรัน SQL เพิ่มเมื่อมี SQL 01 และ 02 แล้ว: SQL 01 ให้สิทธิ์ `insert (code, name, is_active)` และ `update (name, is_active)` พร้อม RLS เฉพาะ Admin ส่วน SQL 02 เพิ่มเงื่อนไข Google มหาลัย ไม่มีการให้สิทธิ์ DELETE หรือใช้ service-role key

Server Action `src/app/(admin)/admin/settings/actions.ts` ตรวจบัญชีและ role ซ้ำก่อนอ่านหรือเขียน ใช้เฉพาะชื่อตารางและคำสั่งที่อนุญาต ไม่รับ role จากฟอร์ม รหัส `code` ของรายการใหม่เป็น UUID ของคำขอที่คงเดิมเมื่อลองซ้ำ อาศัย unique constraint เดิมป้องกันการเพิ่มซ้ำหากคำขอแรกบันทึกสำเร็จแต่การตอบกลับขาดหาย ไม่รับประกันว่าชื่อรายการจะไม่ซ้ำ เพราะ schema เดิมกำหนด unique เฉพาะ code

การแก้ไขใช้ `id` และ `updated_at` เพื่อไม่เขียนทับรายการที่ Admin คนอื่นเปลี่ยนไปแล้ว เมื่อข้อมูลเก่า ระบบโหลดรายการล่าสุดและให้เปิดแก้ไขใหม่ การบันทึกสำเร็จ revalidate layout ของทั้ง `/admin` และ `/user` เพื่ออัปเดตชื่อที่ join ในรายการ รายละเอียด สถิติ และตัวเลือก

อ่านข้อมูลใน `src/lib/admin-settings.ts` แบบแบ่งหน้า ไม่ตัดรายการที่เกินขีดจำกัด API ถ้าโหลดไม่ได้จะแสดงข้อผิดพลาดพร้อมปุ่มลองใหม่

## ตรวจสอบ

รัน `node --test tests/admin-settings.test.mjs` ครอบคลุมการปฏิเสธ User/anonymous การปลอมชื่อตาราง/คำสั่ง การเพิ่มซ้ำหลังคำตอบขาดหาย การแก้ข้อมูลเก่า การเปิด–ปิดโดยไม่ลบ การ revalidate สองพื้นที่ และข้อผิดพลาด การทดสอบนี้ใช้ client จำลอง ไม่เปลี่ยนข้อมูล Supabase จริง

ตรวจรับกับโปรเจกต์จริง: ใช้บัญชี Admin เพิ่มรายการ ทดสอบแก้ชื่อ ปิดและเปิดกลับ แล้วโหลด `/user/report` ใหม่เพื่อตรวจตัวเลือก ตรวจว่าเรื่องแจ้งเก่ายังเปิดได้ บัญชี User ต้องเข้า settings และเขียนตารางเหล่านี้ไม่ได้ตาม RLS เดิม
