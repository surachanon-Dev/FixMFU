# ส่งเรื่องแจ้งซ่อมจริง

หลังตั้ง Google Login และ SQL 01–02 แล้ว ให้ทำตามนี้:

1. Supabase → SQL Editor → New query คัดลอก **ทั้งไฟล์** `supabase/sql/03_submit_reports.sql` แล้ว Run หนึ่งครั้ง รอ `Success. No rows returned`
2. ต้องมี Storage bucket `ticket-photos` แบบ **Private** จำกัด JPG/PNG/WebP และขนาดต่อไฟล์ 2 MB ตามคู่มือเดิม ไม่เปิด Public bucket หรือปิด RLS
3. เริ่ม Next.js ใหม่ (`Ctrl+C` แล้ว `npm run dev`) เพราะตั้ง Server Action body limit เป็น 3 MB เพื่อรับรูป 2 MB พร้อมข้อมูลฟอร์ม
4. เปิด `http://localhost:3000/user/report` ล็อกอินด้วย Google มหาลัย กรอกหัวข้อ อาคาร ห้อง/จุดที่พบ หมวดหมู่ รายละเอียด แล้วแนบรูปได้ไม่เกิน 3 รูป รวม 2 MB หรือส่งโดยไม่แนบรูปก็ได้
5. กดส่ง ปุ่มแสดงกำลังส่งและป้องกันกดซ้ำ สำเร็จแล้วเปิดรายละเอียดพร้อมหมายเลข `REQ-...` กลับ “เรื่องของฉัน” หรือรีเฟรชแล้วต้องยังเห็นเรื่องนั้น

หาก SQL 03 ยังไม่ได้รัน ฟอร์มจะแสดงข้อความติดตั้งระบบ/อัปโหลดไม่สำเร็จ ไม่แสดงความสำเร็จปลอม

## พฤติกรรมและสิทธิ์

- อาคารและหมวดหมู่มาจากแถวที่เปิดใช้งานใน Supabase โดยส่ง UUID จริง ไม่ใช้ชื่ออาคารตัวอย่างเป็นรหัส
- Server Action ยืนยัน Google session และ profile ซ้ำ ไม่รับ reporter/status/role จากฟอร์ม
- ตรวจข้อความและไฟล์ฝั่งเซิร์ฟเวอร์ อ่านและ decode รูปจริงด้วย `sharp` รองรับภาพนิ่ง JPG/PNG/WebP ไม่เกิน 16 ล้านพิกเซล แปลงเป็น WebP ก่อนอัปโหลด ไม่เก็บต้นฉบับในเบราว์เซอร์หรือ localStorage ถาวร
- รูปเข้าถัง Private ผ่าน Storage API ก่อน จากนั้น RPC `submit_repair_report` ตรวจเจ้าของไฟล์ ขนาด ชนิด และ path จริง แล้วสร้าง ticket + attachment metadata + created event ใน transaction เดียว การส่งล้มเหลวไม่สร้าง ticket บางส่วน
- รหัสคำขอและชื่อไฟล์คงเดิมเมื่อลองซ้ำในฟอร์มเดิม RPC คืนเรื่องเดิมเฉพาะเมื่อเจ้าของและข้อมูลตรงกัน ไม่สร้างเรื่องหรือประวัติซ้ำ ถ้าข้อมูลเดิมบันทึกแล้วจะไม่เขียนทับ
- ถ้าอัปโหลดบางรูปไม่สำเร็จก่อนเรียก RPC จะพยายามล้างไฟล์ที่เพิ่งอัปโหลดผ่าน Storage API หากไม่แน่ใจว่า RPC commit สำเร็จหรือยัง จะคงรูปไว้ให้ลองซ้ำ ไม่ลบไฟล์ที่อาจเชื่อมกับเรื่องแล้ว รูปที่ถูกทิ้งหลังปิด/รีเฟรชฟอร์มหรือขาดการเชื่อมต่ออาจค้างโดยยังไม่เชื่อมกับเรื่อง ต้องล้างผ่าน Storage API ภายหลัง ไม่ลบแถว `storage.objects` โดยตรง
- ผู้ใช้เห็นเฉพาะเรื่องที่ตนแจ้ง รวมถึง Admin ที่เข้าพื้นที่ User จะเห็นเฉพาะเรื่องของตน RLS ยังป้องกันข้อมูลระหว่างบัญชี รูปใช้ signed URL อายุ 15 นาที โหลดหน้าใหม่เพื่อรับ URL ใหม่
- สิทธิ์ Storage เพิ่มเฉพาะอัปโหลดใหม่ อ่านรูปที่ตนมีสิทธิ์ และล้างรูปของตนที่ยังไม่ส่งเป็นเรื่อง ห้ามแก้ทับหรือลบรูปที่เชื่อมกับเรื่องแล้ว

## ขอบเขตปัจจุบัน

หน้า User ฟอร์ม ประวัติ และรายละเอียดใช้ Supabase จริง ฝั่ง Admin อ่านรายการ รายละเอียดพร้อมข้อมูลผู้แจ้ง รูป Dashboard และรายงานสรุปจากฐานข้อมูลเดียวกันแล้ว ไม่ต้องเพิ่ม SQL หลัง 03 สำหรับการอ่าน มีปุ่มอัปเดตข้อมูล และแบ่งหน้าอ่านครบแม้มีมากกว่า 1,000 เรื่อง การรับเรื่อง หมายเหตุ ปิดงานพร้อมผล/รูป และยกเลิกเปิดใช้หลังติดตั้ง SQL 04 ตาม [คู่มือ Admin](admin-ticket-actions.md) ส่วนหน้าตั้งค่าและกระดิ่งยังเป็น UI ตัวอย่าง

## ตรวจสอบ

รัน `node --test tests/auth.test.mjs tests/dashboard.test.mjs tests/report.test.mjs tests/admin-reports.test.mjs tests/admin-ticket-actions.test.mjs`, `npm run lint` และ `npm run build -- --webpack`

`supabase/tests/03_submit_reports.test.sql` ใช้เฉพาะฐานข้อมูลแยกสำหรับทดสอบที่จำลอง Storage metadata เท่านั้น **ห้ามนำชุดทดสอบนี้ไปรันใน SQL Editor ของ Supabase จริง** เพราะไม่อัปโหลดไฟล์ผ่าน Storage API ชุดทดสอบครอบคลุม atomic submit, retry, การอ่านข้ามบัญชี, สิทธิ์ Admin, การปลอม owner, anonymous, personal Gmail, password session และห้ามแก้/ลบรูปที่ผูกกับเรื่องแล้ว ข้อมูลจำลอง rollback ทั้งหมด

หลังติดตั้ง SQL 03 ต้องทดสอบด้วยบัญชีจริงอีกครั้ง: ส่งเรื่องแบบไม่มีรูป/มีรูป → ดูรายละเอียดและรีเฟรช → ล็อกอินบัญชีอื่นแล้วเปิด URL เดิมต้องไม่เห็น → ตรวจกับ `tickets`, `ticket_attachments`, `ticket_events` และ Storage โดยไม่เผย token หรือ secret

ตรวจฝั่ง Admin เพิ่ม: เปิด /admin/tickets ดูเรื่องที่ส่งจาก User ค้นหาด้วยหมายเลข REQ และกรองสถานะ เปิดรายละเอียดต้องเห็นผู้แจ้งและรูปตรงกัน Dashboard และรายงานต้องนับจากเรื่องจริง บัญชี User ปกติเปิด Admin ต้องถูกปฏิเสธ
