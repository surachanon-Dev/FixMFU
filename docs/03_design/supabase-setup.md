# ตั้งค่าฐานข้อมูล FixMFU ทีละขั้น

คู่มือนี้สำหรับโปรเจกต์ Supabase ว่าง ใช้ SQL Editor โดยยังไม่ต้องติดตั้ง Supabase CLI และไม่ต้องใส่คีย์ลงในเว็บ ขั้นนี้สร้างฐานข้อมูลเท่านั้น หน้าเว็บยังใช้ข้อมูลตัวอย่างตามเดิม

## 1. เลือกโปรเจกต์

เปิด https://supabase.com/dashboard แล้วเลือกโปรเจกต์สำหรับ FixMFU ตรวจชื่อโปรเจกต์ให้ถูกต้อง ถ้ามีตารางเดิมชื่อเดียวกับด้านล่างให้ตรวจโครงสร้างก่อน ใช้สคริปต์นี้กับโปรเจกต์ว่าง ไม่ลบตารางเพื่อแก้ปัญหาชื่อซ้ำ

## 2. สร้างตารางด้วย SQL Editor

1. ในโปรเจกต์เปิด **SQL Editor** แล้วสร้าง **New query**
2. เปิดไฟล์ `supabase/sql/01_initial_schema.sql` ในโปรเจกต์นี้
3. คัดลอกเนื้อหา **ทั้งไฟล์** ไปวางใน query โดยใช้ role เจ้าของฐานข้อมูล (ปกติคือ `postgres`)
4. กด **Run** เพียงครั้งเดียว เมื่อสำเร็จจะแสดงข้อความสำเร็จ เช่น `Success. No rows returned`
5. ถ้ามี error ให้เก็บข้อความ error เพื่อวิเคราะห์ สคริปต์อยู่ใน transaction จึงไม่สร้างฐานข้อมูลค้างเพียงบางส่วน ถ้า session ยังขึ้น transaction aborted ให้รัน `rollback;` ก่อนคำสั่งถัดไป ไม่จำเป็นต้องลบตาราง

สคริปต์เป็นไฟล์ setup ที่เก็บเวอร์ชันใน Git **ยังไม่ใช่ migration history ของ Supabase CLI** หากภายหลังใช้ CLI ต้องทำ baseline จากฐานข้อมูลที่ตั้งไว้ก่อน ไม่รันสคริปต์เริ่มต้นซ้ำบนฐานเดิม

## 3. ตรวจว่าครบ 6 ตาราง

เปิด **Table Editor** เลือก schema `public`:

| ตาราง | หน้าที่ | ข้อมูลหลังตั้งค่า |
|---|---|---|
| `profiles` | ชื่อ ข้อมูลติดต่อ และบทบาทของบัญชี Auth | ว่าง ถ้ายังไม่มีบัญชี Auth |
| `buildings` | อาคารสำหรับเลือกในฟอร์ม | อาคาร E4, M-Square, หอพัก F1 |
| `categories` | หมวดหมู่สำหรับเลือกในฟอร์ม | แอร์/ประปา, ไฟฟ้า, อินเทอร์เน็ต |
| `tickets` | เรื่องแจ้ง สถานที่ ผู้แจ้ง และสถานะ | ว่าง |
| `ticket_attachments` | ข้อมูลไฟล์รูปและตำแหน่งใน Storage | ว่าง |
| `ticket_events` | ประวัติการดำเนินงาน | ว่าง |

Supabase สร้าง `auth.users` ให้เอง จึงไม่ต้องสร้างตารางเก็บรหัสผ่าน

ตรวจข้อมูลตั้งต้นได้ใน SQL Editor:

```sql
select code, name, is_active from public.buildings order by code;
select code, name, is_active from public.categories order by code;

select tablename, rowsecurity
from pg_tables
where schemaname = 'public'
  and tablename in ('profiles', 'buildings', 'categories', 'tickets', 'ticket_attachments', 'ticket_events')
order by tablename;
```

ผลสุดท้ายต้องมี 6 แถว และ `rowsecurity = true` ทุกแถว

## 4. สิทธิ์ที่เตรียมในขั้นนี้

- ผู้ที่ยังไม่ล็อกอินอ่านตารางเหล่านี้ไม่ได้
- User อ่านโปรไฟล์ เรื่อง รูปแนบ และประวัติของตัวเอง พร้อมแก้ชื่อ/ข้อมูลติดต่อของตัวเองได้
- User สร้างเรื่องของตัวเองได้เฉพาะสถานะ `pending` เวลาและเลขเรื่องสร้างจากฐานข้อมูล บันทึกประวัติการสร้างเรื่องอัตโนมัติ
- Admin อ่านเรื่องและข้อมูลที่เกี่ยวข้องได้ทั้งหมด เพิ่มหรือปิดใช้งานอาคาร/หมวดหมู่ได้
- บัญชีใหม่ได้บทบาท `user` เสมอ แม้มีผู้ส่ง `role: admin` มากับข้อมูลสมัคร ผู้ใช้แก้คอลัมน์ `role` ผ่าน API ไม่ได้ การกำหนด Admin ครั้งแรกจะทำผ่านช่องทางผู้ดูแลที่เชื่อถือได้ในขั้น Auth
- ยังไม่เปิดการแก้สถานะเรื่อง การเขียนหมายเหตุ หรือการเขียนรูป/ประวัติจาก client งานเหล่านี้ต้องเพิ่ม API/RPC ที่ตรวจสิทธิ์และบันทึกประวัติในขั้นถัดไป Admin จึงยังเปลี่ยนสถานะผ่าน client ไม่ได้เช่นกัน
- schema `fixmfu_private` เป็นฟังก์ชันภายใน ไม่เพิ่ม schema นี้ในรายการ Data API exposed schemas
- ชื่ออาคาร/หมวดหมู่ที่ปิดใช้งานแล้วยังอ่านได้เพื่อแสดงเรื่องเก่า แต่สร้างเรื่องใหม่ด้วยรายการที่ปิดใช้งานไม่ได้
- บัญชีที่มีเรื่องแจ้งอยู่จะถูกจำกัดการลบเพื่อรักษาประวัติ ต้องออกแบบกระบวนการลบ/ปกปิดบัญชีก่อนใช้งานจริง

สิทธิ์ใน SQL Editor ของเจ้าของฐานข้อมูลข้าม RLS ได้ การเห็นทุกแถวใน SQL Editor จึงไม่ได้แปลว่า User อ่านทุกแถวได้

## 5. ทดสอบสิทธิ์ก่อนเชื่อมเว็บ

ในโปรเจกต์พัฒนา เปิด query ใหม่แล้วรัน **ทั้งไฟล์** `supabase/tests/01_initial_schema.test.sql`

สคริปต์สร้างบัญชี/เรื่องทดสอบชั่วคราว ไม่ส่งอีเมล และสลับ role เพื่อทดสอบ User สองคน Admin และผู้ไม่ล็อกอิน ตรวจการแอบกำหนด Admin การปลอมผู้แจ้ง การแก้สถานะตรง ๆ ประวัติการสร้างเรื่อง และจำนวน/ขนาดข้อมูลรูปแนบ จากนั้น rollback ข้อมูลทดสอบทั้งหมด

ผลสุดท้ายต้องเป็น `PASS: FixMFU database foundation` ถ้าทดสอบไม่ผ่านให้รัน `rollback;` ใน session เดิมก่อน และเก็บข้อความ error

การทดสอบในเครื่องด้วย PGlite ใช้ PostgreSQL พร้อมโครง `auth.users`/`auth.uid()` จำลอง จึงยังต้องทดสอบสคริปต์นี้บนโปรเจกต์ Supabase พัฒนาจริงเพื่อยืนยันพฤติกรรม Auth/สิทธิ์ของระบบที่จัดการโดย Supabase

## 6. เตรียมที่เก็บรูปภายหลังตารางผ่านแล้ว

เปิด **Storage** → **New bucket**:

- ชื่อ `ticket-photos`
- **Public bucket: ปิด** (private)
- จำกัดชนิดไฟล์ `image/jpeg`, `image/png`, `image/webp`
- จำกัดไฟล์แต่ละไฟล์ไม่เกิน **2 MB**

ข้อจำกัด bucket เป็นขนาด **ต่อไฟล์** ส่วนกติกา **3 รูป ขนาดรวม 2 MB ต่อเรื่อง/ประเภท** ต้องตรวจที่ API ร่วมกับ trigger ข้อมูลแนบที่เตรียมไว้ ไม่ใช่กฎ bucket เพียงอย่างเดียว ในขั้นนี้ยังไม่เพิ่ม policy อัปโหลด/ดาวน์โหลด จึงยังใช้งานรูปจากหน้าเว็บไม่ได้

ตำแหน่งไฟล์ที่ออกแบบไว้คือ `<ticket UUID>/<report หรือ repair>/<attachment UUID>.<นามสกุล>` เช่น `report` สำหรับรูปจากผู้แจ้ง และ `repair` สำหรับผลการแก้ไข เก็บชื่อไฟล์เดิมใน `original_name` และตำแหน่งใน `object_path` ไม่เก็บ base64 หรือ URL ที่หมดอายุลงฐานข้อมูล

API ในขั้นถัดไปต้องตรวจไฟล์จริง ผู้แนบ สถานะเรื่อง รวมถึงลบไฟล์ที่อัปโหลดค้างเมื่อบันทึกข้อมูลล้มเหลว และจัดสิทธิ์อ่านรูปให้เจ้าของเรื่อง/Admin ก่อนเปิดใช้งาน

## ขั้นถัดไป: Google มหาวิทยาลัย

ปัจจุบันเปลี่ยนเป็น Google Login เฉพาะ `@lamduan.mfu.ac.th` แล้ว ให้ทำตาม [คู่มือ Google มหาวิทยาลัย](google-university-login.md) เพื่อรัน SQL 02 เปิด hook และตั้ง OAuth ก่อนใช้งานจริง ใช้บัญชี Google มหาลัยสร้างบัญชีอัตโนมัติ

เมื่อยืนยันว่าตารางและสิทธิ์ผ่านแล้ว จะเชื่อม Supabase Auth กับ Next.js กำหนดบัญชี Admin และเพิ่ม API/RPC สำหรับส่งเรื่องพร้อมรูป รับเรื่อง เพิ่มหมายเหตุ และปิดงาน โดยรักษา transaction ของการเปลี่ยนสถานะและประวัติร่วมกัน

### เตรียมค่าเชื่อมต่อเว็บ

1. เปิดโปรเจกต์ Supabase แล้วกด **Connect** ด้านบน
2. คัดลอก **Project URL** และ **Publishable key** สำหรับโปรเจกต์นี้
3. ในโฟลเดอร์ FixMFU คัดลอก `.env.example` เป็น `.env.local` หากยังไม่มีไฟล์นี้ แล้วกรอกค่าหลัง `=` ของทั้งสองบรรทัด

```dotenv
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=
NEXT_PUBLIC_SITE_URL=http://localhost:3000
```

เลือก Publishable key (`sb_publishable_...`) สำหรับตัวแปรนี้ ไม่ใช้ Secret key หรือ `service_role` ซึ่งมีสิทธิ์สูงกว่า `.env.local` ถูก Git ignore ส่วน `.env.example` เก็บเฉพาะชื่อช่องว่างเพื่อให้เพื่อนในทีมตั้งค่าเองได้ หากมี `.env.local` อยู่แล้วให้แก้เฉพาะสองตัวแปรนี้โดยรักษาค่าอื่นไว้

มี client สำหรับ browser/server, Proxy รีเฟรช session, หน้า `/login` และปุ่มออกจากระบบแล้ว เริ่มเซิร์ฟเวอร์ Next.js ใหม่ให้โหลดค่าที่เพิ่ม เมื่อ Auth พร้อมแล้ว ติดตั้ง SQL 03 ตาม [คู่มือส่งเรื่อง](report-submission.md) เพื่อเชื่อมฟอร์ม รูป และประวัติฝั่ง User ส่วน Admin อ่านรายการ รายละเอียด และสถิติจริงแล้ว แต่ยังไม่เปิดการเปลี่ยนสถานะ

### สร้างบัญชีเริ่มต้นเพื่อทดสอบล็อกอิน

เปิด `/login` แล้วใช้ปุ่ม Google ด้วยบัญชีมหาลัย หลังตั้งค่าตาม [คู่มือ Google มหาวิทยาลัย](google-university-login.md) ครบ ระบบสร้าง `profiles` ด้วย role `user` อัตโนมัติ คู่มือเดียวกันมีขั้นทดสอบการปฏิเสธ Gmail ส่วนตัวและการกำหนดบัญชี Admin ผ่าน UUID ที่เจ้าของโปรเจกต์เลือก การทดสอบอัตโนมัติในเครื่องยังไม่แทนการยืนยัน OAuth จริงจากบัญชีมหาลัย

หากเชื่อมต่อหรืออ่านโปรไฟล์ไม่ได้ ระบบจะปฏิเสธการเข้าและแสดงหน้าข้อผิดพลาด ไม่กำหนดสิทธิ์สำรองเป็น User/Admin อัตโนมัติ หน้า Auth และ portal ใช้ `Cache-Control: private, no-store` เพื่อไม่แชร์ข้อมูล session ผ่าน cache
